# PDF 知识库问答系统

基于 FastAPI、LangChain 和 LangGraph 构建的 PDF 知识库问答项目。

用户可以通过网页上传 PDF、查看文档列表并针对文档内容提问。系统结合关键词检索和向量检索，经过重排与证据充分性判断，生成带来源提示的回答。

本项目用于学习和实践 RAG、Agent 编排、问答评估及 Web 服务开发，目前以本地单机运行为主。

## 功能

- **PDF 文档管理**：上传、列表查询、入库状态展示和删除。
- **文档入库**：PDF 文本提取、文本切分、Embedding 和 Chroma 存储。
- **混合检索**：结合 BM25 关键词检索与向量语义检索。
- **查询改写**：生成查询变体，扩展检索范围。
- **结果重排**：使用 Cross-Encoder 对候选片段重新排序。
- **证据判断**：判断检索内容是否足以回答问题，信息不足时返回提示。
- **网页问答**：通过 FastAPI 提供文档管理与问答接口。
- **评估与追踪**：接入 LangSmith，并使用 Ragas 指标评估回答。

## 工作流程

### 文档入库

1. 用户上传 PDF。
2. 检查文件大小、后缀和 PDF 标记。
3. 计算文件哈希，保存文件并登记数据库记录。
4. 提取文本并切分为片段。
5. 计算文本向量并写入 Chroma。
6. 更新文档入库状态。

### 知识库问答

1. 接收用户问题。
2. 改写问题，生成多个检索查询。
3. 分别执行 BM25 和向量检索。
4. 使用 RRF 融合各路排名，累计同一片段的贡献并输出去重结果。
5. 使用重排模型筛选相关片段。
6. 判断证据是否充分。
7. 基于上下文生成回答；证据不足时返回提示。

> 多查询检索保留每个查询的独立排名，再进行 RRF 融合；不能先拼接去重，否则会丢失原始排名及多路命中信息。重排、改写和证据判断是否开启，以具体实验配置为准。

## 数据存储

| 数据 | 保存位置或方式 |
|---|---|
| 上传后的 PDF | `RAGProject/data/pdfs/` |
| PDF 名称、路径、大小和状态 | SQLite |
| 文本片段、来源信息和向量 | `RAGProject/chroma_store/`（Chroma） |
| BM25 检索器 | 进程内存 |

BM25 可根据 Chroma 中保存的文本片段重建。知识库新增、删除或更新文档后，需要同步刷新 BM25 和运行中的检索图。

SQLite 与 Chroma 是独立存储，不会自动同步。删除文档时，需要分别处理文件、数据库记录和向量片段。

## 本地运行

### 1. 准备环境

当前开发环境为 Windows、Conda 和 PyCharm。

已有开发环境可执行：

```powershell
conda activate project02
```

在仓库根目录 `MyProject/` 安装依赖：

```powershell
python -m pip install -r requirements.txt
```

### 2. 配置模型与存储

参考根目录 `.env_example` 配置本地环境变量，并按照 `RAGProject/config.py` 的读取逻辑配置：

- LLM API Key。
- LLM 服务地址与模型名称。
- 本地 Embedding 模型路径。
- 本地重排模型路径。
- Chroma 持久化目录与集合名称。
- 检索数量、切块参数和证据判断阈值。

注意区分：

- **模型目录**：保存模型权重、配置和分词器。
- **向量库目录**：保存 Chroma 数据。
- **集合名称**：向量库中使用的 collection 名称。

不要将真实 API Key 或密码提交到仓库。

### 3. 启动服务

以下命令从仓库根目录 `MyProject/` 执行，先进入应用目录，以匹配 `from backend...`、`from utils...` 等顶层导入方式：

```powershell
cd RAGProject
python -m uvicorn main:app
```

保持在 `RAGProject/` 目录，开发时如需修改代码后自动重启：

```powershell
python -m uvicorn main:app --reload
```

访问地址：

- 网页：`http://127.0.0.1:8000/`
- API 文档：`http://127.0.0.1:8000/docs`

首次启动需要加载模型，可能需要等待一段时间。

### 4. 使用系统

1. 打开网页并上传 PDF。
2. 等待入库完成。
3. 在文档列表中检查入库状态。
4. 输入与文档内容相关的问题。
5. 查看回答并核对来源。

## 评估设计与实测结果

### 数据与统计口径

基于“青杉科技”虚构公司制度语料构建40条问答，划分为20条开发集和20条测试集，覆盖条款编号查询、语义表达、条件判断、版本区分及无答案场景。开发集用于调参与排查问题，测试集用于检验确定后的方案。

- 开发集：17条可回答题、3条无答案题。
- 测试集：18条可回答题、2条无答案题，以结果文件中的 `metadata.answerable` 标注为准。
- 使用 Ragas 对检索上下文和最终回答评分，各指标为逐题分数的算术平均值，保留三位小数。
- 延迟来自结果记录中的 `latency_seconds`，为单题回答流程耗时，不含评估器评分耗时；P50按样本中位数计算。
- 以下三个结果文件各包含20条记录，均未记录目标函数或评估器错误。

### 开发集：向量检索与 RRF 融合

Vector 为纯向量检索基线；RRF 为 BM25 与向量检索的排名融合方案。两组记录来自同一开发集。表格反映已保存运行结果，严格的消融实验还需固定生成提示词、模型、上下文数量及其他配置。

| 方案 | 评估范围 | 样本数 | Context Precision | Context Recall | Faithfulness | Answer Relevancy |
|---|---|---:|---:|---:|---:|---:|
| Vector | 全部开发题 | 20 | 0.875 | 1.000 | 0.975 | 0.697 |
| RRF | 全部开发题 | 20 | 0.875 | 1.000 | 0.889 | 0.698 |
| Vector | 可回答题 | 17 | 0.971 | 1.000 | 0.971 | 0.820 |
| RRF | 可回答题 | 17 | 0.971 | 1.000 | 0.938 | 0.821 |

| 方案 | 计时范围 | 平均延迟 | P50延迟 |
|---|---|---:|---:|
| Vector | 全部20条开发题 | 1.85秒 | 1.67秒 |
| RRF | 全部20条开发题 | 4.86秒 | 4.44秒 |

**结果解读：**本轮开发集记录中，RRF 没有提高 Context Precision 或 Context Recall，回答相关性变化很小，忠实度下降且耗时增加。因此当前数据不支持“增加 RRF 就能提升整体效果”的结论。需要逐题检查融合排序、无关证据及回答中的额外事实，再决定采用哪种方案。

### 测试集：RRF 融合

| 方案 | 评估范围 | 样本数 | Context Precision | Context Recall | Faithfulness | Answer Relevancy |
|---|---|---:|---:|---:|---:|---:|
| RRF | 全部测试题 | 20 | 0.960 | 1.000 | 0.853 | 0.764 |
| RRF | 可回答题 | 18 | 1.000 | 1.000 | 0.837 | 0.798 |

全部20条测试题回答延迟：平均 **5.42秒**，P50 **5.13秒**，不含评估模型评分耗时。

**结果解读：**可回答题的检索指标较高，但忠实度仍有改进空间，说明“检索到证据”不等于“最终回答中的事实都有依据”。下一步应检查低分样本中的额外推断、条件改写和证据使用情况。

目前尚未提供同一测试集上的纯向量运行记录，不能用 Vector 开发集结果与 RRF 测试集结果计算提升幅度。

### 指标含义与边界

| 指标 | 评估含义 | 主要比较内容 |
|---|---|---|
| Faithfulness | 回答中的事实是否有上下文支持 | 最终回答与实际用于生成的检索文本 |
| Answer Relevancy | 回答是否切题 | 由回答反推的问题与原问题的语义相似度 |
| Context Precision | 有用片段是否排在前面 | 检索片段、问题与参考答案，并结合排名评分 |
| Context Recall | 参考答案中的事实是否被上下文覆盖 | 参考答案与检索文本 |

- Context Precision **不是回答正确率**，这里也不是简单的“相关块数 / Top-K”。
- 无答案题单独分析：正确拒答的 Answer Relevancy 也可能偏低；常规 Precision / Recall 不足以衡量拒答质量。
- 本次未单独计算拒答正确率，不能把上述分数解释为拒答成功率。
- Context Recall 为1.000仅表示该指标在这些样本上的评分，不能证明整个知识库没有漏检。
- 数据规模较小、语料为虚构制度，LLM评分也存在波动，结果不代表生产环境效果。
- 评分异常、NaN或调用失败应单独记录，不能直接当作0分混入平均值。

## BM25 中文检索问题定位与修复

### 问题现象

查询 `FIN-2026-024的付款起算条件是什么？` 时，知识库中确实包含该条款，但调试输出中所有文档的 BM25 得分均为0，相关条款无法依靠词项匹配排到首位。

修复前的查询词项：

```python
['FIN-2026-024的付款起算条件是什么？']
```

### 根因与定位

默认空白切分没有把连续中文问题拆成有效词项，整句被当成一个词，难以与制度正文中的词项匹配。该问题来自 BM25 文本预处理，不是条款缺失，也不能通过单纯提高 RRF 中 BM25 的权重解决。

定位过程：

1. 确认文档中存在 `FIN-2026-024`，排除未入库或正文缺失。
2. 打印查询分词结果，发现整句只有一个词项。
3. 查看逐文档 BM25 得分，确认所有得分均为0。
4. 修正分词并重建检索器后，再检查对应条款的排名与得分。

### 修复方式

- 使用中文分词处理正文及查询。
- 通过编号识别规则保留 `FIN-2026-024` 等完整条款编号，避免被拆散。
- 统一大小写，使正文和查询中的编号采用相同表示。
- 文档与查询使用同一套预处理函数。
- 清除旧 BM25 缓存并重建索引，避免继续使用旧词项统计。

修复后的查询词项：

```python
['fin-2026-024', '的', '付款', '起', '算', '条件', '是', '什么']
```

### 验证结果

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 查询词项 | 整句作为单个词项 | 中文词项与完整条款编号 |
| 目标条款得分 | 0.0 | 约4.19 |
| 排名表现 | 无法按有效匹配区分文档 | 对应条款排在首位 |

修复后首位正文包含：

> FIN-2026-024 付款时限：资料齐全且财务审核通过后，原则上5个工作日内付款。

这里的4.19是这条查询在当前语料上的 BM25 匹配分数，不是概率、准确率或可跨语料比较的质量指标。该案例验证了词项匹配恢复；整体效果仍需通过问答集对比检验，不能将该分数直接解释为整体效果提升。

## 当前限制

- 当前主要面向本地单机学习场景。
- 入库与问答使用进程内锁串行执行，并发能力有限。

- 问答接口返回完整答案，尚未实现流式输出。

- SQLite、Chroma 和 BM25 之间的一致性需要应用代码维护。
- 自动评估分数不能替代人工检查。
